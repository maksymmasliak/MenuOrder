# MenuOrder — специфікація

QR-меню для кафе. Чистий PHP без фреймворку.

## Суть і межі

Гість сідає за столик і сканує QR-код. Відкривається меню закладу. Гість збирає кошик і натискає «Замовити». Через секунду персонал отримує в Telegram-групу повідомлення із замовленням і номером столика. Адміністратор у вебадмінці керує меню, цінами й столиками.

Межі MVP: один заклад, без онлайн-оплати (гість платить офіціанту як зазвичай), без статусів замовлення для гостя.

Чому без фреймворку: система маленька, адмін один, публічна частина — дві сторінки й один ендпоінт. Фреймворк дав би більше залежностей, ніж користі. Межа, за якою варто переходити на Laravel: кілька закладів, онлайн-оплата, ролі персоналу, кухонний екран у реальному часі.

## Стек

- PHP 8.4 без фреймворку (php-fpm), розширення `pdo_mysql`, `gd`, `curl`.
- MySQL 8 (InnoDB, `utf8mb4`, strict `sql_mode`).
- Composer:
  - runtime: `endroid/qr-code`, `vlucas/phpdotenv`;
  - dev: `phpunit/phpunit`, `phpstan/phpstan` (рівень 6+), `friendsofphp/php-cs-fixer`.
  - Інші залежності — лише після дозволу автора.
- Фронтенд гостя: Vue 3 + Vite. Збірка в `public/assets/`.
- Адмінка: серверні PHP-шаблони, без Vue.
- Docker Compose на основі власного шаблону автора.

## Ролі

| Роль | Хто це | Що може |
|---|---|---|
| Гість | Анонімний відвідувач, без реєстрації | Переглядає меню, оформлює замовлення зі свого столика |
| Адмін | Акаунт, створений консольною командою | Керує категоріями, стравами, столиками; переглядає замовлення |
| Персонал | Не користується системою напряму | Отримує замовлення в Telegram-групі |

«Особа» гостя — це столик, з якого він відсканував QR-код. Публічної реєстрації немає ні для кого.

## Сценарії

Гість:

1. Сканує QR → відкривається `/t/7/a3f9c2e1b4d8e6f0`.
2. Сервер перевіряє підпис, запам'ятовує столик у сесії та перенаправляє на `/menu`.
3. Гість бачить категорії й страви з фото та цінами. Архівних страв і неактивних категорій не видно.
4. Додає страви в кошик. Кошик живе в `localStorage` браузера, сервер про нього не знає.
5. За бажанням пише коментар («без цибулі», до 200 символів).
6. Натискає «Замовити» → `POST /api/orders`.
7. Бачить «Замовлення №184 прийнято, очікуйте». Кошик очищається.

Адмін:

1. Входить на `/admin/login`.
2. Створює категорії, задає їхній порядок і активність.
3. Створює страви: назва, опис, ціна, фото. Змінює ціни. Архівує страви, яких більше немає, і за потреби повертає з архіву.
4. Додає столики й друкує їхні QR-коди однією сторінкою.
5. Переглядає замовлення й бачить ті, що не дійшли в Telegram. Може поставити їх на повторне надсилання.

Персонал: отримує повідомлення в Telegram і обслуговує замовлення.

Збій Telegram: гість отримує «прийнято» в будь-якому разі, бо замовлення вже в базі. Повідомлення персоналу доставляється повторними спробами, а якщо всі спроби невдалі, замовлення видно в адмінці з позначкою «не доставлено».

## Модель даних

- Гроші — у копійках, `INT UNSIGNED`. Жодних `FLOAT`/`DECIMAL` у розрахунках.

## Бізнес-правила

**R1. Підписаний столик.** QR веде на `/t/{tableId}/{sig}`, де `sig` — перші 16 символів `hash_hmac('sha256', "table:{tableId}", APP_SECRET)`. Перевірка — лише через `hash_equals()`. Невірний підпис або неактивний столик → сторінка «QR-код недійсний, зверніться до офіціанта».

**R2. Столик у сесії.** Після успішної перевірки `table_id` і час входу записуються в сесію. Прив'язка діє 3 години. Замовлення без дійсного столика в сесії відхиляється (403). Номер столика з тіла запиту сервер ігнорує.

**R3. Ціну рахує сервер.** Клієнт надсилає лише `dishId`, кількість і коментар. Ціни й суму сервер бере з бази. Будь-яка ціна в запиті ігнорується.

**R4. Валідація замовлення:**

- від 1 до 30 різних позицій;
- кількість кожної — від 1 до 20;
- кожна страва існує, не архівна, а її категорія активна;
- коментар — до 200 символів, без керівних символів;
- однакові `dishId` у запиті зливаються в одну позицію (кількості додаються, далі перевіряється ліміт 20).

**R5. Атомарність.** Замовлення з позиціями — один агрегат: `OrderRepository::save()` зберігає його в одній транзакції. `OrderService` перевіряє R4 до `save()`. Якщо хоч одна позиція невалідна, не створюється нічого.

**R6. Ліміт запитів:**

- не більше 5 замовлень з одного столика за 10 хвилин;
- не більше 10 замовлень з одного IP за 10 хвилин;
- перевищення → 429 з повідомленням «Забагато замовлень, зверніться до офіціанта».

**R7. Перше надсилання.** Після коміту транзакції — одна синхронна спроба надіслати повідомлення в Telegram з таймаутом 5 секунд. Успіх → `sent`. Невдача → статус лишається `pending`, лічильник спроб +1, текст помилки записується. Гість отримує «прийнято» в будь-якому разі.

**R8. Повторні спроби (cron щохвилини):**

- вибираються замовлення `pending`, де спроб менше 5 і минула пауза від останньої спроби;
- пауза росте: 1, 2, 4, 8 хвилин після 1-ї, 2-ї, 3-ї, 4-ї невдачі;
- після 5-ї невдачі → `failed`, і адмін бачить це в адмінці;
- скрипт захищений від одночасного запуску (`flock` на файл блокування), щоб два cron-процеси не надіслали одне замовлення двічі.

> **Відкрите питання R7/R8 (вирішує автор у задачі T17, до того не реалізовувати жодного варіанту).**
> Сценарій гонки: замовлення закомічене зі статусом `pending`, `telegram_attempts = 0`, `telegram_last_attempt_at = NULL`. Поки веб-запит чекає відповідь Telegram (до 5 с), cron може вибрати це саме замовлення й надіслати його вдруге. `flock` від цього не захищає: він синхронізує cron з cron, а не з веб-запитом.
> Відома межа навіть після фіксу: якщо Telegram прийняв повідомлення, а відповідь загубилася або впав UPDATE статусу, буде дубль. Гарантія — at-least-once.
> Рішення записати сюди і в `docs/decisions.md`.

**R9. Екранування.** Повідомлення йде з `parse_mode=HTML`, тому назви страв і коментар гостя проходять через `htmlspecialchars`. Інакше коментар з `<b>` зламає розмітку або Telegram відхилить повідомлення.

**R10. Архівування.** Архівна страва зникає з меню гостя, але лишається в адмінці (фільтр «Архів») і в старих замовленнях. Повернення з архіву робить її знову доступною.

**R11. Повторна постановка в чергу.** Адмін може повернути `failed`-замовлення в `pending`: лічильник спроб скидається, і cron підхоплює його на найближчому запуску.

## Формат повідомлення в Telegram

```
Замовлення №184
Столик: 7
Час: 19:42

- Картопля фрі x 2 = 140,00 грн
- Бургер класичний x 1 = 245,00 грн
- Лимонад x 2 = 120,00 грн

Коментар: Без цибулі в бургері

Разом: 505,00 грн
```

Час — у `Europe/Kyiv`. Можна додати емодзі й жирний шрифт (`<b>Разом: 505,00 грн</b>`). Ліміт Telegram — 4096 символів; з лімітами R4 повідомлення вміщується.

Налаштування бота:

1. Створити бота через @BotFather, отримати токен.
2. Додати бота в групу персоналу.
3. Написати в групу будь-яке повідомлення й отримати `chat_id` групи через `getUpdates` (для груп — від'ємне число).
4. Записати токен і `chat_id` у `.env`.

| Код | Коли | Приклад тіла |
|---|---|---|

## Фронтенд гостя (Vue 3 + Vite)

- Код у `frontend/`, збірка (`vite build`) у `public/assets/` з маніфестом. `/menu` — PHP-оболонка, яка підключає зібрані файли.
- **Той самий origin, що й API.** Прив'язка столика живе в PHP-сесії (R2), тому запити до `/api/*` мають іти з того ж домену й порту, з cookie сесії. CORS не налаштовуємо.
- У dev-режимі Vite dev server проксіює `/api`, `/t`, `/uploads` на nginx (або навпаки — nginx проксіює на Vite), щоб cookie працювали так само, як на проді.
- Стан кошика — у `localStorage`; ціни в кошику лише для відображення, сервер їх ігнорує (R3).
- Обробка відповідей 403 / 422 / 429 / 500 з людськими повідомленнями.
- Без Vue Router і без бібліотек стану, якщо не з'явиться реальна потреба. Нові npm-залежності — лише після дозволу автора.

## Безпека

- Паролі: `password_hash()` / `password_verify()`.
- Сесія: `session_regenerate_id(true)` після входу адміна; cookie `HttpOnly`, `Secure` на проді, `SameSite=Lax`; вихід знищує сесію.
- CSRF: токен у кожній формі адмінки, перевірка через `hash_equals()`.
- Ліміт входу: 5 невдалих спроб за 15 хвилин на пару email + IP (та сама таблиця `rate_limit_hits`).
- Виведення: у PHP-шаблонах лише через хелпер `e()`. У Vue — лише текстова інтерполяція, без `v-html`.
- База: тільки prepared statements, `PDO::ATTR_EMULATE_PREPARES = false`, `ERRMODE_EXCEPTION`.
- Завантаження фото: MIME через `finfo` (лише jpeg, png, webp), розмір до 2 МБ, випадкове ім'я файлу, оригінальне ім'я не використовується, у папці завантажень заборонено виконання PHP (правило nginx).
- Публічний ендпоінт: ліміти R6, валідація R4, ціни з бази R3.
- Секрети: `APP_SECRET`, токен бота (`app/.env`), доступ до бази (кореневий `.env`) — лише в `.env`-файлах, які в `.gitignore`.

**Відоме обмеження.** QR-код можна сфотографувати й замовляти не з закладу. Пом'якшення: прив'язка на 3 години (R2), ліміти (R6), персонал бачить номер столика. При зловживаннях — новий `APP_SECRET` і передрук QR. Описати чесно в README.

```
  migrate.php            <- застосовує SQL-міграції по черзі
  create-admin.php       <- створення адміна з консолі
  retry-telegram.php     <- cron: повторні спроби (R8)

migrations/
  001_init.sql
src/
  Http/                  <- Router, Request, Response, JsonResponse, ErrorHandler
  Controller/
    Public/              <- TableEntry, Menu, Order
    Admin/               <- Auth, Category, Dish, Table, Order
  Service/
    OrderService         <- валідація і розрахунок (R3-R4), збереження через атомарний OrderRepository::save() (R5)
    TableSigner          <- підпис і перевірка QR (R1)
    RateLimiter          <- R6 і ліміт входу
    TelegramNotifier     <- HTTP-запит до Bot API

```

Принципи:

- Контролери тонкі: розібрати запит → викликати сервіс → віддати відповідь.
- Логіка правил (R1, R3–R6, R8, R9) — у сервісах, які не знають про HTTP.
- Залежності збираються вручну в `bootstrap.php`: DI-контейнер не потрібен.
- Роутер, Request/Response, обробник помилок, CSRF, завантаження файлів пишуться з нуля. З попередніх проєктів береться лише PDO-шаблон автора.
- Час у сервісах — через ін'єкцію «годинника» (інтерфейс з `now()`), щоб тести могли підмінити час.

## Інфраструктура

Docker Compose на основі шаблону автора (адаптувати під MySQL і PHP 8.4):

| Сервіс | Що це |
|---|---|
| `app` | php-fpm 8.4 з `pdo_mysql`, `gd`, `curl` |
| `nginx` | статика, проксі на PHP, заборона виконання в `uploads/` |
| `db` | MySQL 8.4 (`docker/compose/mysql.yaml`, підключається через `COMPOSE_FILE`) |
| `node` | Node LTS для `npm install`, `vite` dev server і `vite build`; під профілем `front` |
| `cron` | той самий образ, що й `app`, планувальник — supercronic (від `www-data`, бачить env контейнера); щохвилини `retry-telegram.php`, щоночі `cleanup.php` |

Тестова база — окрема (`menuorder_test`), створюється init-скриптом при першому старті `db` (на порожньому томі).

Два `.env`, обидва в `.gitignore`, у git — лише `.env.example` для кожного.

Кореневий `.env` — для Docker (порти, образ, доступ до БД). `DB_*` compose передає і в MySQL, і в контейнери `app`/`cron` як змінні оточення (`DB_HOST=db`, `DB_PORT=3306`):

```
COMPOSE_PROJECT_NAME=menuorder
COMPOSE_FILE=compose.yaml:docker/compose/mysql.yaml
HOST_APP_PORT=8080
HOST_DB_PORT=3307
HOST_VITE_PORT=5173
DB_NAME=menuorder
DB_USER=menuorder
DB_PASSWORD=...
DB_ROOT_PASSWORD=...
TEST_DB_SUFFIX=_test
```

`app/.env` — для застосунку (phpdotenv, `createImmutable`: змінні оточення з compose не перезаписуються):

```
APP_ENV=dev
APP_URL=http://localhost:8080
APP_SECRET=...           # для HMAC столиків і хешу IP
TELEGRAM_BOT_TOKEN=...
TELEGRAM_CHAT_ID=...
```

Makefile: `up`, `down`, `sh`, `migrate`, `test`, `stan`, `cs` (перевірка, dry-run), `cs-fix` (виправлення), `admin`, `front-dev`, `front-build`.

Деплой: бот лише надсилає повідомлення, вебхук не потрібен. Дешевий VPS з тим самим Compose і Caddy для HTTPS. `APP_URL` на проді — реальний домен: від нього залежать посилання в QR.
